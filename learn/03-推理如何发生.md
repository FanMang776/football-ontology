# 03 推理如何发生：物化、声明与推断

> 本章配套 `python scripts/explore.py --step 3`。前置：读完 [02-用本体建模电商业务](02-用本体建模电商业务.md)。

## OWL-RL 物化：把逻辑结论一次算全

第 02 章说"类成员沿 subClassOf 向上传递"，这个"传递"是谁执行的？答案是推理机。本项目的做法是最朴素也最直观的一种：**物化（materialization）**——加载时把 OWL-RL 规则集能推出的所有结论一次性算全，放进同一张图里，之后的查询就是在普通图上做模式匹配，没有任何隐藏的推理步骤。

`engine/loader.py` 的核心函数，全文：

```python
def materialize(g: Graph) -> Graph:
    """在副本上运行 OWL-RL 推理闭包，返回物化后的图。

    axiomatic_triples=False / datatype_axioms=False：关掉 OWL 词汇表的公理三元组，
    否则"推断三元组"里会混入上千条和业务无关的公理，无法教学演示。
    """
    m = Graph()
    for t in g:
        m.add(t)
    DeductiveClosure(OWLRL_Semantics, rdfs_closure=True,
                     axiomatic_triples=False, datatype_axioms=False).expand(m)
    return m
```

逐参数说明（owlrl 7.6.2）：

- `OWLRL_Semantics`——启用 OWL 2 RL 规则集。OWL-RL 是 OWL 的可判定子集，为规则引擎的正向链式推理设计：每条规则形如"前提 → 结论"，反复应用直到不动点。我们用到的传递性、对称性、逆属性、subClassOf 传播都在其中；
- `rdfs_closure=True`——连同 RDFS 闭包一起算（`rdfs:subClassOf` 传播类型成员就是 RDFS 语义，不是 OWL）；
- `axiomatic_triples=False`、`datatype_axioms=False`——**关键的教学开关**。OWL 词表自带一批恒真公理（比如"所有类都是 rdfs:Resource 的子类"、数据类型的定义三元组），默认会物化出上千条与业务无关的三元组。对生产推理无碍，对"看推断清单学推理"的教学目标是噪音，所以关掉。

## 声明 vs 推断：一条真实的 diff

跑 `python scripts/explore.py --step 3`，实际输出（数字均为真实运行结果）：

```

有代表性的推断（前 30 条）：

  [推断] b_music        isComponentOf      b_ultimate
  [推断] b_ultimate     hasPart            p_amp
  [推断] b_ultimate     hasPart            p_bt01
  [推断] p_amp          compatibleWith     p_bt01
  [推断] p_amp          isComponentOf      b_music
  [推断] p_amp          isComponentOf      b_ultimate
  [推断] p_bt01         isComponentOf      b_music
  [推断] p_bt01         isComponentOf      b_ultimate
  [推断] p_bt02         sameSeries         p_bt01
  [推断] p_buds         substituteFor      p_bt02
  [推断] p_x2           substituteFor      p_bt01
  [推断] p_amp          type               cat_digital_acc
  [推断] p_bt01         type               cat_digital_acc
  [推断] p_bt01         type               cat_electronics
  ...
```

390 条声明里没有任何一条说"BT-01 是数码配件"，也没有一条说"全家桶包含 BT-01"——推断区里的 779 条全部是推理机从公理中走出来的。`b_ultimate hasPart p_amp` 是传递性 + 逆属性联合工作的产物：声明层写了 `b_music hasPart p_amp` 和 `b_ultimate hasPart b_music`，传递得 `b_ultimate hasPart p_amp`，再由 `inverseOf` 补出 `p_amp isComponentOf b_ultimate`。

Web 界面的「图谱总览」Tab 把这个 diff 做成了视觉语言：声明边实线，推断边虚线。点开任意商品实体，「实体详情」里 declared / inferred 两栏就是同一件事的列表形态。

## 为什么 VIP 规则不进 OWL 层

看到这里容易产生一个误会：既然推理这么强，"年消费超 5000 就是 VIP"为什么不也交给 OWL？因为 **OWL-RL 表达不了算术和聚合**。它擅长的是分类学与结构逻辑（传递、对称、逆、包含），而 `annualSpend > 5000` 是数值比较，"订单数 ≥ 3"要对订单计数——这两件事 OWL 一条规则都写不出来。

所以本项目把含算术/聚合的业务规则放进单独一层，用 SPARQL CONSTRUCT 表达。`engine/rules.py` 真实代码：

```python
VIP_SPEND = PREFIX + """
CONSTRUCT { ?c a ex:VIPCustomer . }
WHERE {
    ?c a ex:Customer ; ex:annualSpend ?s .
    FILTER(?s > %(spend)d)
}
"""

VIP_SILVER = PREFIX + """
CONSTRUCT { ?c a ex:VIPCustomer . }
WHERE {
    { SELECT ?c (COUNT(DISTINCT ?o) AS ?n)
      WHERE { ?o ex:placedBy ?c . } GROUP BY ?c }
    ?c ex:membershipLevel "silver" .
    FILTER(?n >= %(min_orders)d)
}
"""
```

注意产物是什么：`?c a ex:VIPCustomer`——**一条类型三元组**。规则层的产出和 OWL 层的产出是同一种东西（三元组），所以能无缝并入同一张图供下游查询。这正是第 02 章思考题 2 的答案：`VIPCustomer` 这个类放在 TBox 里供规则"往里装"，但 ABox 永远不写 `a ex:VIPCustomer`——它是纯粹由规则推断出的类别，落库反而会在阈值调整后变成脏数据。

这套设计的另一个好处：阈值是函数参数。`apply_vip_rules(g, spend_threshold=5000, min_orders=3)`，Web「客户分类」Tab 上拖动阈值滑块，每次都是全量重算，不存在"改了阈值忘了刷新存量数据"这类经典 bug。

## 自反 subClassOf 的坑

OWL-RL 有一个不细看文档就会踩的行为：它会物化**自反的** `rdfs:subClassOf` 边——推理后图里出现 `cat_headphone rdfs:subClassOf cat_headphone` 这样的自环。这在语义上没错（子类关系确实自反），但会毒杀一类朴素查询。

第 02 章的语义推荐里有个"朴素版"：找出同品类商品。直觉实现是 `?p a ?cat . ?other a ?cat`，但物化后 BT-01 同时属于 cat_headphone、cat_digital_acc、cat_electronics 三层——不加限定，"同品类"会泄漏成整棵子类树（BT-01 的"同品类"会包括充电器和音箱）。`engine/queries.py` 的真实代码和注释：

```python
# 朴素推荐：同品类其他商品。品类成员关系（?other a ?cat）本身是子类推理的结果；
# 用 cat_ 前缀限定排除 Product/Bundle 这类结构性父类。
# 关键一步：物化后 ?p 会同时带上全部祖先品类（cat_headphone → cat_digital_acc →
# cat_electronics），若不限定"最具体品类"，"同品类"会泄漏成整棵子类树。
# NOT EXISTS 要求该品类下没有 ?p 也属于的更细子类，从而只命中叶子品类；
# 注意排除 ?sub = ?cat——OWL-RL 会物化自反的 subClassOf 边，不排除则全查询落空。
NAIVE_SAME_CATEGORY = PREFIX + """
SELECT DISTINCT ?other ?label WHERE {
    ?p a ?cat . ?other a ?cat ; rdfs:label ?label .
    ?cat a owl:Class .
    FILTER(STRSTARTS(STR(?cat), "http://example.org/ecom#cat_"))
    FILTER(?other != ?p)
    FILTER NOT EXISTS {
        ?sub rdfs:subClassOf ?cat . ?p a ?sub .
        FILTER(?sub != ?cat)
    }
} ORDER BY ?other
"""
```

`FILTER(?sub != ?cat)` 那一行就是自反边留下的疤：没有它，"该品类下没有更细子类"这个条件永远不会成立（自反边让 `?sub` 总能取到 `?cat` 自己），查询一条结果都不返回。教训值得记住：**推理层的输出会进入查询层的输入，写查询时必须知道图被物化成了什么样**。运行 `--step 4` 可以看到它的实际效果——BT-01 的朴素推荐只有"蓝牙耳机 BT-02、无线耳塞 Buds3、头戴耳机 X2"三条，没有泄漏。

## 五层心智模型

物化只是推理层。运行时知识在 `engine/knowledge_base.py` 的模块 docstring 里被组织成五层：

```python
"""知识库引擎：声明层 + 撤销层 + 效果层 + 推理 + 规则，全部内存态。

分层（自底向上）：
  declared    schema.ttl + data.ttl（不可变）
  retractions 运行时撤销的声明事实（如把活动状态从 active 撤下）——撤销也是写回
  effects     运行时新增的事实（供应商延迟、通知标记、补货标记……）
  material    (declared − retractions + effects) 过 OWL-RL 闭包
  rule_out    VIP 分类规则 + 动作规则的产出（每次刷新重算，是推论不是数据）
"""
```

三层事实、两层派生。事实层做代数：`declared − retractions + effects` 得到当前有效的事实集；派生层做推理：事实集过 OWL-RL 闭包得 `material`，再过规则层得 VIP 与动作建议。

两层派生物**永远不落库、每次刷新全量重算**——这是整个设计里最省心的一条纪律。事实层的状态只有 `declared/retractions/effects` 三个集合，物化图和规则输出从它确定性导出，任何时候 `refresh()` 一次就全图一致，不存在缓存失效问题。

`retractions` 层值得单独停一下。直觉上"撤销"是"删除"，容易想成 `declared.remove(t)`。但删除声明事实同样是一种**对知识库的修改**，和新增事实地位对等——所以把它建模成一个独立的"撤销清单"层，与 effects 对称。docstring 里那句"撤销也是写回"说的就是这个。为什么要这么绕？因为 `declared` 必须保持不可变：它是每次 `refresh()` 的基准输入，如果允许原地删，"重置回初始状态"就无处可退了（第 04 章的 PausePromotion 会真的用到这层）。

## 思考题

1. 把 `VIP_SPEND` 里的 `FILTER(?s > 5000)` 改写成 OWL 公理为什么做不到？如果要支持"消费额落在 [3000, 5000] 区间是金卡"，应该写在哪一层？
2. `retractions` 层为什么不能直接从 `declared` 图里 remove 那条三元组？分别从"重置功能"和"审计（谁在何时撤销了什么）"两个角度想。
3. 自反 `subClassOf` 边会让 `api/main.py` 里的 `/api/taxonomy` 递归构建函数无限爆栈（源码注释里写了这件事）。这个 bug 为什么在生产代码里更危险——推理层的一条边能杀死的是"看起来毫不相干"的接口层。
