# 03 · 推理如何发生：声明 vs 推断

> 配套实验：`python scripts/explore.py --step 3`

## 图谱有两层

`engine/loader.py` 开头写着本项目的核心心智模型：

> 声明的三元组（declared）：schema.ttl + data.ttl 里白纸黑字写的
> 推断的三元组（inferred）：推理机物化出来的，永远不落库、随事实即时重算

跑一下实验台：

```bash
python scripts/explore.py --step 3
```

你会看到：**声明 312 条 → 物化后 887 条，新推断 575 条**。多出来的 575 条没有一个字是写进文件的——它们全部是公理的推论，每次加载重算，改一条事实它们就跟着变。

## 推理一：位置泛化（语义传递）

data.ttl 里，德布劳内只有一行声明：

```turtle
ex:p_am1 a ex:Player, ex:AttackingMidfielder ;
```

他从来没有被写上"前腰是场上位置的一员"。但物化后你可以查到：

```
ex:p_am1 a ex:AttackingMidfielder   ← 声明
ex:p_am1 a ex:Position              ← 推断（AttackingMidfielder ⊑ Position）
```

因为 schema.ttl 里有一条公理：`ex:AttackingMidfielder rdfs:subClassOf ex:Position`。OWL-RL 推理机沿着 `subClassOf` 边把成员关系**向上传播**。

这就是第一章留下的那个问题的答案：位置建模成类型成员而不是字符串字段，就是为了**让"属于大类"这件事可以被推理自动补全**。促销推广一个品类、商品自动被覆盖——电商里的老例子；换成足球：中场缺人时问"谁能踢中场"，`a ex:Midfielder` 的查询自动覆盖所有中场子位置——同一套公理，换了个业务皮。

## 推理二：青年队归类

`ex:YouthPlayer rdfs:subClassOf ex:Player` 一条公理，六个青年队球员就自动是 `Player`——没有写任何一行"青年队球员也是球员"的代码。教程第二章的判定测试锁死了这个行为：

```python
assert (EX.p_yam1, RDF.type, EX.Player) in g   # 推断
assert (EX.p_yam1, RDF.type, EX.AttackingMidfielder) in g  # 声明
```

看 `web/` 图谱总览：实线是声明的边，**虚线是推理出来的边**。点开任意球员抽屉，事实分两栏——"声明的事实"和"推断的事实"。

## 有事实，不等于有理解

到这里停一下，感受推理的边界：

- 推理擅长：**分类学与结构逻辑**。"B费是前腰" → "B费是场上位置的一员"，这类结论机器自己算。
- 推理不擅长：**算术和聚合**。"体能 56 算不算过度使用"要比较阈值和数场次，OWL 闭包干不了这个。

所以本项目把含算术的业务规则放在 OWL 之外的一层（`engine/rules.py`，SPARQL CONSTRUCT/SELECT），产出**并回同一张图**。下一章你会看到完整的分工：推理管"是什么类"，状态计算管"现在怎么样"，规则层管"该怎么办"。
