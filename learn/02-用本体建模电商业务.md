# 02 用本体建模电商业务

> 本章配套 `python scripts/explore.py --step 2`，需要先读完 [01-本体是什么](01-本体是什么.md)。

## 品类是类，不是属性

建模电商业务，第一个分歧点就出在"品类"上。直觉做法是给商品加一个 `category` 属性：

```
p_bt01  category  "headphone"      # 直觉做法（本项目没有这么做）
```

本项目选了另一条路——**品类即类（categories-as-classes）**，直接把品类树建成 `subClassOf` 树。`ontology/schema.ttl` 原文：

```turtle
# 品类即类：品类树就是 subClassOf 树
ex:cat_electronics a owl:Class ; rdfs:subClassOf ex:Product ; rdfs:label "电子产品"@zh .
ex:cat_digital_acc a owl:Class ; rdfs:subClassOf ex:cat_electronics ; rdfs:label "数码配件"@zh .
ex:cat_headphone   a owl:Class ; rdfs:subClassOf ex:cat_digital_acc ; rdfs:label "耳机"@zh .
ex:cat_charger     a owl:Class ; rdfs:subClassOf ex:cat_digital_acc ; rdfs:label "充电设备"@zh .
ex:cat_cable       a owl:Class ; rdfs:subClassOf ex:cat_digital_acc ; rdfs:label "线材"@zh .
ex:cat_audio       a owl:Class ; rdfs:subClassOf ex:cat_digital_acc ; rdfs:label "音频设备"@zh .
ex:cat_speaker     a owl:Class ; rdfs:subClassOf ex:cat_audio ; rdfs:label "音箱"@zh .
```

于是"给商品归类"就写成类型声明。`data.ttl` 里 BT-01 的归类方式：

```turtle
ex:p_bt01 a ex:PhysicalProduct ; rdfs:label "降噪蓝牙耳机 BT-01"@zh ;
    ... ;   # suppliedBy / price / stock 等属性略
    a ex:cat_headphone ;
```

BT-01 是耳机。注意这句没有写"BT-01 属于数码配件"，也没有写"BT-01 是电子产品"——但两者都是真的，因为类成员关系会沿着 `subClassOf` **向上传递**：`p_bt01 a cat_headphone` 加上 `cat_headphone ⊑ cat_digital_acc ⊑ cat_electronics ⊑ Product`，推理机可以自己走完这条链。

把品类建成类而不是属性值，换来三个能力：

1. **祖先成员自动成立**——声明最细一层的归属，上层归属由推理补全，永不失同步；
2. **品类可以直接当主语和宾语**——`promo_618 promotes cat_digital_acc`（促销推广一个品类）在属性建模下要绕中间表，在这里是一条普通三元组；
3. **品类可以有身份**——品类与商品之间能建关系（促销↔品类），品类与品类之间能建关系（替代品类、兼容品类），属性值做不到。

运行 `python scripts/explore.py --step 2` 可以打印整棵类树（实际输出，注意 VIPCustomer 也挂在树里，它的来历见第 03 章）：

```
BusinessObject（业务对象）
  Action（决策动作）
    ...
  Product（商品）
    Bundle（捆绑套装）
    PhysicalProduct（实体商品）
    cat_electronics（电子产品）
      cat_digital_acc（数码配件）
        cat_audio（音频设备）
          cat_speaker（音箱）
        cat_cable（线材）
        cat_charger（充电设备）

```

## 属性公理的威力：传递、对称、逆

类层级只是推理的一半，另一半在属性上。`schema.ttl` 给几个关键谓语附加了公理：

```turtle
ex:hasPart        a owl:ObjectProperty , owl:TransitiveProperty ; rdfs:label "包含"@zh .
ex:isComponentOf  a owl:ObjectProperty ; owl:inverseOf ex:hasPart ; rdfs:label "是…的组成部分"@zh .
ex:substituteFor  a owl:ObjectProperty , owl:SymmetricProperty ; rdfs:label "替代"@zh .
ex:compatibleWith a owl:ObjectProperty , owl:SymmetricProperty ; rdfs:label "兼容"@zh .
ex:sameSeries     a owl:ObjectProperty , owl:SymmetricProperty ; rdfs:label "同系列"@zh .
```

五行声明，各自换来一类免费推理。拿数据里最深的一个例子看——`data.ttl` 中全家桶与音乐套装是这么声明的：

```turtle
ex:b_ultimate a ex:Bundle ; rdfs:label "全家桶套装"@zh ;
    ex:price 1899 ; ex:stock 12 ;
    ex:hasPart ex:b_music , ex:p_spk1 .
ex:b_music a ex:Bundle ; ... ;        # label / price / stock 略
    ex:hasPart ex:p_bt01 , ex:p_amp .
```

全家桶包含音乐套装，音乐套装包含 BT-01。数据里**没有任何一行**说"全家桶包含 BT-01"，但从这三条声明加 `hasPart` 的传递性，推理机能得出 `b_ultimate hasPart p_bt01`、`b_ultimate hasPart p_amp`——嵌套任意深度的套装，一次推理穿透。

对称属性（`SymmetricProperty`）让反向免写：数据里只写了 `p_bt01 substituteFor p_x2`，但"x2 替代 bt01"同样成立；`sameSeries`、`compatibleWith` 同理。逆属性（`inverseOf`）则让两个方向的边只存一份：写了 `b_music hasPart p_bt01`，`p_bt01 isComponentOf b_music` 就是自动的。

这三类公理在本项目里都有一条真实查询在消费它们：第 04 章风险传导的第 2 步——"延迟供应商的商品影响了哪些套装"——就是靠 `isComponentOf`（逆）+ `hasPart`（传递）一条查询直达任意嵌套深度。如果用关系库实现，你得写递归 CTE，还得保证写入时双向同步；在这里，公理替你同步。

## 决策动作也进本体

这个模型里最不寻常的决定：把"可执行的业务动作"也建成类。`schema.ttl` 原文：

```turtle
# 决策动作——本体不仅描述业务，也描述"可做的事"
ex:Action              rdfs:subClassOf ex:BusinessObject ; rdfs:label "决策动作"@zh .
ex:PausePromotion      rdfs:subClassOf ex:Action ; rdfs:label "暂停促销"@zh .
ex:NotifyCustomer      rdfs:subClassOf ex:Action ; rdfs:label "通知客户"@zh .
ex:CreatePurchaseOrder rdfs:subClassOf ex:Action ; rdfs:label "生成采购单"@zh .
ex:PromoteSubstitute   rdfs:subClassOf ex:Action ; rdfs:label "推荐替代品"@zh .
```

为什么动作要进本体？因为"情况 → 应该做什么"的映射本身就是业务知识，和"耳机属于数码配件"是同一级别的东西。动作成为类之后：

- 动作实例是图上的节点，携带 `hasTarget`（对谁执行）、`hasReason`（为什么）——一条建议动作在图里是自解释的；
- 规则层产出的建议动作是**推断**，不是落库数据（第 04 章展开）；
- 执行器按动作类型分发，类型就是 `a ex:PausePromotion` 这一行。

## 本章动手

先跑一遍：

```bash
python scripts/explore.py --step 2
```

然后做一次真实建模。打开 `ontology/data.ttl`，在商品区追加一个新品类和商品（可直接粘贴）：

```turtle
# 新品类：游戏外设，挂在数码配件下
# （加到 schema.ttl 品类区）
# ex:cat_gaming a owl:Class ; rdfs:subClassOf ex:cat_digital_acc ; rdfs:label "游戏外设"@zh .

# 新商品（加到 data.ttl 商品区）
ex:p_pad a ex:PhysicalProduct ; rdfs:label "电竞鼠标垫"@zh ;
    ex:suppliedBy ex:sup_hongda ; ex:price 69 ; ex:stock 400 ;
    a ex:cat_gaming .
```

重启后，无需写任何额外代码，以下结论是**自动推理出来**的（在 Web 界面「图谱总览」Tab 点开 p_pad，或用 `--step 3` 验证）：

- `p_pad a ex:Product`、`p_pad a ex:BusinessObject`——沿 `subClassOf` 链向上；
- `p_pad a ex:cat_digital_acc`、`p_pad a ex:cat_electronics`——品类祖先成员；
- 若把它加进某个套装：`p_pad isComponentOf <套装>`（逆属性）以及**该套装的全部祖先套装**都包含它（传递性）；
- 宏达配件若在「风险传导」Tab 被标记延迟，`p_pad` 立即出现在受影响商品清单里——查询只认 `suppliedBy`，不认识"鼠标垫"。

你写的是两行类声明加一条商品数据，得到的是一整张推理网络里的新节点。这就是"数据即模型"的含义。

## 思考题

1. 如果把品类退回属性建模（`ex:category "耳机"`），第 04 章里"促销推广品类 `promo_618 promotes cat_digital_acc`"这条三元组该如何表达？"促销覆盖其品类下所有商品"这条规则要付出什么额外代价？
2. `compatibleWith` 声明为对称属性后，`data.ttl` 里只写了 `p_ch65 compatibleWith p_bt01`，界面上却能查到 BT-01 兼容充电器。若两方向都手写声明，有什么维护风险？
3. 试着给 `ex:suppliedBy` 也声明 `owl:SymmetricProperty`——为什么这在语义上是错的？（对称的是"替代"，不是"供应"。选公理时，先问这个关系在业务里是否天然可逆。）
