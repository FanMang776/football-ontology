# 04 从查询到决策：让本体做业务判断

> 本章配套 `python scripts/explore.py --step 4` 和 `--step 5`。前置：读完 [03-推理如何发生](03-推理如何发生.md)。

前三章建立了模型和推理，本章回答最后的问题：**怎么让这套东西替业务做决定**。答案是一条传导链：本体回答"世界是什么样"，规则回答"这种情况下该做什么"，执行器负责"做了之后世界真的变了"。用一个场景把三层串起来：**供应商声科电子宣布延迟交付**。

## 风险传导五步

在 Web「风险传导」Tab（或 `--step 4`）里把声科电子标记为延迟，后端 `engine/scenarios.py` 的 `risk_chain` 返回一份五步风险视图，每一步都自带解释和它依赖的公理/规则。`--step 4` 的实际输出：

```
== 场景 1：声科电子延迟的风险传导 ==
  第 1 步（3 项）：suppliedBy 关系直接反查：哪些商品由该供应商供应
  第 2 步（2 项）：isComponentOf 逆属性 + hasPart 传递推理：套装在任意嵌套深度受影响
  第 3 步（2 项）：促销覆盖面：直接推广商品、推广其套装、或推广其品类（品类归属来自子类推理）
  第 4 步（5 项）：订单→明细→商品路径：包含受影响商品的待发货订单
  第 5 步（3 项）：叠加规则层推断的 VIP 客户：需要优先安抚的高价值客户
```

逐步拆解（计数为实际运行结果）：

| 步 | 结果 | 消费的知识 |
|---|---|---|
| 1. 受影响商品（3 项） | BT-01、BT-02、Hub6 | `suppliedBy` 直接反查，一条 SPARQL，无推理 |
| 2. 受影响套装（2 项） | 音乐套装、全家桶 | `isComponentOf`（逆属性物化）+ `hasPart`（传递性物化）——查询 `engine/queries.py` 的 `BUNDLES_OF_PRODUCT` 只有一行模式 `?p ex:isComponentOf ?b`，任意嵌套深度直达 |
| 3. 受影响促销（2 项） | 数码配件 618 大促、音乐套装限时购 | `PROMOS_TOUCHING_PRODUCT` 的三分支 UNION（下节细讲）；"BT-01 属于数码配件"来自第 03 章的子类推理 |
| 4. 待发货订单（5 项） | o1、o3、o4、o8、o14 | `订单→hasLine→明细→lineProduct→商品` 路径 |
| 5. 受影响 VIP（3 项） | 张伟、李娜、王磊 | 叠加规则层推断的 `VIPCustomer`（第 03 章） |

注意第 2 步：数据里只写了 `b_ultimate hasPart b_music`，全家桶受影响是推理出来的。换成关系库，这一步是递归 CTE；在这里是一条普通查询，因为**深度已经被公理消化掉了**。

## 决策规则层：情况 → 动作的映射

知道了风险在哪，下一步是"该做什么"。`engine/rules.py` 里四条动作规则各自匹配一种情况，`Q_PAUSE` 是其中最有讲解价值的一条，全文：

```python
Q_PAUSE = prepareQuery(PREFIX + """
SELECT DISTINCT ?p ?promo WHERE {
    ?sup ex:status "delayed" .
    ?p ex:suppliedBy ?sup .
    ?promo a ex:Promotion ; ex:status "active" .
    { ?promo ex:promotes ?p . }
    UNION { ?promo ex:promotes ?b . ?p ex:isComponentOf ?b . }
    UNION { ?promo ex:promotes ?c . ?p a ?c . ?c a owl:Class . }
}
""")
```

逐行读：

- 前三行圈定情况——存在延迟供应商、它供了商品 `?p`、存在进行中的促销 `?promo`；
- **分支一** `?promo ex:promotes ?p`：促销直接推广该商品本身（本数据集的促销都指向品类或套装，此分支暂无命中，但语义上必须补全）；
- **分支二** `?p ex:isComponentOf ?b`：促销推广的是该商品所属的套装——`isComponentOf` 是逆属性 + 传递的物化产物，所以嵌套套装也命中（音乐套装限时购推广的 b_music 就是靠这条分支匹配到 BT-01 的；若全家桶的促销也在进行中，深层嵌套同样会命中）；
- **分支三** `?promo ex:promotes ?c . ?p a ?c . ?c a owl:Class`：促销推广的是一个**品类**，而该商品属于这个品类。`?c a owl:Class` 把 `?c` 限定为类——促销直接推广的套装（b_music 之类）是实例不是类，被这一句挡在分支三之外，三分支因此各司其职、互不重复：直接商品 / 所属套装 / 所属品类。而品类这一支的威力在于：`?p a ?c` 里的品类成员关系很多是**推理出来的**——BT-01 从未声明"属于数码配件"，是子类推理让它挂上了这个类，于是"推广数码配件的 618 大促"自动覆盖了 BT-01。

三条分支合起来回答了"一个促销到底覆盖哪些商品"——这个问题在 SQL 里要 JOIN 一张"促销-商品"覆盖表，而覆盖表恰恰是最难维护的部分：新品上架、套装改配、商品改类，都得有人记得更新。本体方案里覆盖面是**推导**的，永远和事实一致。

`Q_NOTIFY` 则展示第二类机制：

```python
Q_NOTIFY = prepareQuery(PREFIX + """
SELECT DISTINCT ?cust WHERE {
    ?sup ex:status "delayed" .
    ?p ex:suppliedBy ?sup .
    ?o ex:hasLine ?l . ?l ex:lineProduct ?p .
    ?o ex:orderStatus "pending" ; ex:placedBy ?cust .
    ?cust a ex:VIPCustomer .
    FILTER NOT EXISTS { ?cust ex:notified true }
}
""")
```

情况是"VIP 客户有待发货订单包含延迟商品"——注意 `?cust a ex:VIPCustomer` 依赖的是**规则层推断**而非数据，五层模型在这里叠了起来。而 `FILTER NOT EXISTS { ?cust ex:notified true }` 是防重复建议：通知过一次后效果写回，条件不再成立，建议自动从清单消失。

四条规则的防重机制分两种，`rules.py` 注释里写得很清楚：

```python
# 防重复建议有两种机制，按查询分别说明：
#   1) Q_PAUSE 用正向匹配 ?promo ex:status "active"——活动暂停后条件即不成立；
#   2) Q_NOTIFY / Q_PURCHASE / Q_SUBSTITUTE 用 FILTER NOT EXISTS 前置谓词
#      （notified / restockRequested / promoBoosted）——效果写回后动作从清单消失。
```

规则的产出不是执行，而是**建议**：带确定性 ID（`_action_id` 从类型和目标派生，如 `action_PausePromotion_promo_618`）、目标（`hasTarget`）和自然语言解释（`hasReason`）的动作实例。建议是推论，不落库——每次 `refresh()` 全量重算。

## 执行闭环：效果即事实

建议清单里的动作可以被执行。`engine/actions.py` 的核心是一张效果表：

```python
# PausePromotion 必须撤销声明层的 "active"（data.ttl 里已有），
# 只叠加 "paused" 的话声明层 "active" 仍在物化图里，Q_PAUSE 会永远命中——
# 所以这里用 (新增, 撤销) 二元组：新增走 effects 层，撤销走 retractions 层。
EFFECTS = {
    "PausePromotion": lambda targets: (
        [(targets[0], EX.status, Literal("paused"))],
        [(targets[0], EX.status, Literal("active"))]),
    "NotifyCustomer": lambda targets: (
        [(targets[0], EX.notified, Literal(True))], []),
    "CreatePurchaseOrder": lambda targets: (
        [(targets[0], EX.restockRequested, Literal(True))], []),
    "PromoteSubstitute": lambda targets: (
        [(targets[0], EX.promoBoosted, Literal(True))], []),
}
```

每条效果是 `(新增三元组, 撤销三元组)` 二元组：新增写进第 03 章五层模型的 effects 层，撤销写进 retractions 层，然后 `refresh()` 全量重推。重点看 `PausePromotion`：它**必须撤销**声明层的 `"active"`。只添加 `"paused"` 不够——data.ttl 里声明的 `promo_618 status "active"` 原样还在，物化图里两条 status 并存，Q_PAUSE 的正向匹配永远命中，这个建议就成了打不死的幽灵。"撤销也是写回"（第 03 章）在这里从设计理念变成了正确性刚需。

执行器还带一道回滚防护（`actions.py`）：

```python
    kb.refresh()
    if act in kb.action_reasons:
        # 二次防护：执行后条件应已消除；未消除则回滚本次效果
        for s, p, o in additions:
            kb.effects.remove((s, p, o))
        for s, p, o in retractions:
            kb.retractions.remove((s, p, o))
        kb.refresh()
        return {"ok": False, "message": "动作执行后条件未消除，已回滚"}
```

执行后重推一次，若建议仍在（说明效果没消除触发条件），把刚写的效果撤干净并报告失败。这是"效果即事实"范式自带的验证器：**动作是否生效，问图就知道**。

`--step 5` 的实际输出把闭环跑了一遍：

```
执行动作 action_PausePromotion_promo_618
  原因：活动「数码配件 618 大促」覆盖了延迟供应商供应的「六合一扩展坞 Hub6、蓝牙耳机 BT-02、降噪蓝牙耳机 BT-01」（通过直接推广、推广其所属套装、或推广其所属品类匹配），建议先暂停。
  结果：已执行：…
  图谱三元组 1171 → 1171（效果已作为新事实写回并重新推理）
  剩余建议动作 8 条——已处置的自动消失
```

两个细节值得咀嚼。其一，三元组数没变：撤销一条声明事实、新增一条效果事实，规模恰好抵消——但**内容**变了，618 大促的状态从 active 变成了 paused，下次重推不会再出现在任何建议里。其二，"剩余 8 条"——执行前是 9 条，PausePromotion 执行后它自己从清单上消失了，因为建议本来就是推论：事实变了，推论自然更新。界面上对应「决策中心」Tab 的执行与"全部执行"按钮。

## 工程范式

把本章的三层画出来：

```
┌─────────────────────────────────────────────────┐
│  行动层  engine/actions.py                       │
│  执行建议动作，效果作为事实写回 effects/retractions │
│         ↑ 建议清单（动作实例 + 解释）              │
├─────────────────────────────────────────────────┤
│  决策层  engine/rules.py                         │
│  SPARQL 规则：情况 → 动作建议（推论，不落库）      │
│         ↑ 物化图 + VIP 推断                       │
├─────────────────────────────────────────────────┤
│  语义层  ontology/*.ttl + engine/loader.py       │
│  品类即类、传递/对称/逆公理、OWL-RL 物化          │
│         ↑ 事实：declared − retractions + effects │
└─────────────────────────────────────────────────┘
```

这个分层的价值在于接口稳定：语义层换推理机（OWL-RL 换增量物化、换图数据库的内置推理），决策层一条规则不用改；行动层在本 demo 里是往内存图写三元组，在生产里就是把同一条动作实例翻译成对 CRM/ERP/营销平台的 HTTP 调用——`action_PausePromotion_promo_618` 的形态天然就是一次 `POST /promotions/promo_618/pause` 的载荷。决策层到行动层的接口形态一致，这正是"动作也进本体"（第 02 章）在工程上的回报。

## 什么时候不该用本体

诚实的边界讨论和优点一样重要。以下场景，老老实实用普通技术栈：

- **单表 CRUD**：数据没有需要推理的结构（无分类层级、无传递关系、无跨类规则），本体的公理层无事可做，只剩形式化开销；
- **纯统计报表**：GROUP BY 一把梭的分析需求，列式存储和 SQL 优化器比 SPARQL 引擎快一个量级；
- **高并发热点写路径**：本项目的全量重算模型（每次 refresh 推一遍闭包）依赖数据规模小——390 条声明物化出 1169 条是毫秒级，业务数据到千万级就需要增量推理引擎，那是另一个量级的工程投入。

判断标准可以收敛成一句话：**当业务复杂度主要在"关系与分类的语义"上时，本体把这些语义从应用代码搬进了数据；如果复杂度在别处（并发、算力、流程），本体帮不上忙**。

## 思考题

1. 第 4 步结果里为什么没有陈静？她有 3 笔订单满足银卡 VIP 条件（第 03 章），但订单全是 `shipped` 状态——把订单状态条件从 Q_NOTIFY 里去掉，业务上错在哪？
