# 02 · 用能力问题建模俱乐部世界

> 配套实验：`python scripts/explore.py --step 2`

## 先别急着画类图

第一次建本体的人最容易问："我该建多少个 Class？"——这个问题一问，就已经走偏了。

正确的问题反过来：**你想让机器做什么？** 这些问题叫**能力问题（Competency Questions）**。本体不是把世界画得越大越好，而是"为了具备某种能力，把这个世界需要知道什么描述出来"。

## 两个能力问题，倒推出整个 schema

**能力问题一：「谁受伤会影响下场比赛？」**

要回答它，机器需要知道什么？把它拆开：

| 需要知道 | 对应 schema 里的东西 |
|---|---|
| 谁是球员、谁在俱乐部 | `Player`、`playsFor`、`YouthPlayer ⊑ Player` |
| 他踢什么位置 | 球员 `a` 某个位置类（如 `a ex:AttackingMidfielder`） |
| 位置之间什么关系 | 位置子类树：`AttackingMidfielder ⊑ Position` |
| 他能不能出场 | `injuredWith` → `InjuryRecord` → `weeksOut` |

**能力问题二：「哪些球员过度使用、有伤病风险？」**

| 需要知道 | 对应 schema 里的东西 |
|---|---|
| 他打了多少分钟 | `participatesIn` → `Match`，`minutesPlayed` |
| 训练负荷 | `trainsIn` → `TrainingSession` → `load` |
| 近期状态 | `fitness`（注意：这个**不在** data.ttl 里！它是算出来的，见第四章） |

打开 `ontology/schema.ttl` 对照看：每个公理都是被某个能力问题"逼出来"的，没有一个是"为了完整"画上去的。**这就是 YAGNI 在本体工程里的样子。**

## 类层级树

```bash
python scripts/explore.py --step 2
```

你会看到这棵树：

```
FootballEntity（足球实体）
  Player（球员）
    YouthPlayer（青年队球员）
  Position（场上位置）
    AttackingMidfielder（前腰）
    CentreBack（中后卫）
    ...
  Club / Contract / Match / TrainingSession / InjuryRecord
```

两个建模决定值得停下来想：

1. **位置用双层平铺**：七个叶子位置全部直接挂在 `Position` 下面，没有"中场 ⊑ 位置、前腰 ⊑ 中场"的三层结构。为什么？教学 demo 只需要"最细位置 → 大类"一层泛化推理，多一层只会让闭包更难看懂。
2. **青年队是 Player 的子类**，不是平行的另一个类。这样"青年队球员也是球员"不需要任何额外规则，`YouthPlayer ⊑ Player` 一条公理就说完。

## 动手练：长出一个新概念

理解能力问题驱动建模的最好方式是亲身长一次。试这个：

1. 新能力问题：「**哪些球员的合同快到期、俱乐部有流失风险？**」
2. 反推：需要什么新东西？（提示：`contractYears` 已经存在——差的是"快到期"的**规则**，和一个"流失风险"的**推论**。需要往 `ontology/data.ttl` 加东西吗？）
3. 动手：把你的答案写进 `engine/rules.py`（模仿 `Q_TREATMENT` 的写法），跑 `python -m pytest -q` 确认没破坏别人。

做完这一步，你就体会了那句话：**本体不是一次画完的，是在真实业务问题里一点一点长出来的。**
